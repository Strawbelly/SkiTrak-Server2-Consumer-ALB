  What changed
  - ChannelPool:
    - init() opens one connection and creates all the channels up front
      (default 64).
    - borrowChannel() and returnChannel() hand each channel to one thread at a
      time, and nothing opens a channel per publish.
    - A dead channel is replaced. If the connection drops, the next request
      opens a new one and rebuilds the pool; only one thread does this, even
      under load.
    - While the broker stays down, reconnect attempts are rate-limited, so
      requests fail fast instead of waiting on timeouts.
  - One change from the skeleton: connection is volatile instead of final,
    because a final field can't be swapped out after a reconnect. The queue is
    still final. This is noted in the code and the README.
  - SwipeEventPublisher sends the 9 required fields as JSON. It waits for
    RabbitMQ to confirm receipt, and if a publish fails it retries once on a
    fresh channel.
  - SkierServlet keeps its existing validation and messages. The only new
    behavior: it returns 503 when it can't publish, which the client already
    retries.
  - Settings (broker host, credentials, pool size, server ID and so on) are read
    from system properties or environment variables and documented in
    server/README.md.

  What changed

  Before: Moving resorts between threads by draining each one, plus a placement
  algorithm that minimised moves
  Now: resize(n) stops every worker, starts n new ones, and deals resorts
  round-robin. Each thread gets ⌊R/N⌋ or ⌈R/N⌉ resorts. A stopped worker
  finishes and acks its current message, and closing its channel returns the
  rest to the queue in order, so per-resort ordering still holds.
  ────────────────────────────────────────
  Before: Hand-written reconnect supervisors in the consumer and in the server's

  relay
  Now: The RabbitMQ client's built-in automatic recovery. Only the first
  connection is retried by hand.
  ────────────────────────────────────────
  Before: A separate broadcaster thread that batched updates every 100 ms
  Now: The worker publishes a snapshot to the fanout exchange as soon as
  standings change. It's best-effort: the next change sends the full standings
  again.
  ────────────────────────────────────────
  Before: A separate AutoScaler class
  Now: A small scheduled check in ConsumerPool: add a thread when the backlog is

  too high, remove one when it's nearly empty.
  ────────────────────────────────────────
  Before: EventProcessor, Deduplicator, ConsumerStats, ResortAssigner
  Now: Folded into ResortWorker, LeaderboardAggregator and ConsumerPool.

  Before: Server: LeaderboardHub and SessionSender (queued async sends)

  synchronized

  Trade-offs the simplification introduced
  - Every resize briefly pauses all resorts, not just the ones that move.
  - Scale-down acts on a single quiet check, so the pool can flap up and down.

  - Broadcasts aren't batched. Expect roughly twice the fanout traffic seen in

    that change isn't sent until the next one.

    the other subscribers on that server.

⏺ The consumer module has 9 classes. Messages flow through them in this order:
  RabbitMQ → ResortWorker → LeaderboardAggregator (and TopN) → back to RabbitMQ
  on the fanout exchange.

  Startup and configuration

  - ConsumerApp: the entry point (main).
    - Loads the config and opens the RabbitMQ connection, retrying until the
      broker is reachable.
    - Creates the aggregator and the pool, sets the starting thread count, and
      starts the autoscaler if it's enabled.
    - Logs stats every 10 s and registers a shutdown hook that stops the workers
      and closes the connection.
  - ConsumerConfig: reads all settings from system properties or environment
    variables, falling back to defaults.
    - Covers broker connection details, resort IDs, thread counts (initial, min,
      max), prefetch, autoscale thresholds, top-N size, dedup window size, and
      retry settings.
    - Builds the ConnectionFactory with automatic connection recovery turned on.
  - Topology: holds the RabbitMQ names and declares them on startup. Declaring
    is safe to repeat.
    - The swipe exchange skitrak.exchange and one durable queue per resort
      (skitrak.resort.{id}). Each queue is set to single-active-consumer, so
      only one consumer reads it at a time.
    - The dead-letter exchange and queue (skitrak.dlx and skitrak.dlq).
    - The skitrak.leaderboard fanout exchange.

  Processing

  - ConsumerPool: manages the worker threads.
    - resize(n) stops every worker, then starts n new ones and deals the resorts
      round-robin, so each thread gets an equal share (±1).
    - backlog() totals the ready messages across all resort queues.
    - The autoscaler checks that backlog on a timer and adds or removes one
      thread.
    - Holds the shared counters: duplicates, retries, deadLettered, ackFailures,
      broadcasts.
  - ResortWorker: one thread with its own channel, consuming the resort queues
    it was assigned. Its thread is the only one that acks, rejects or publishes
    on that channel.
    - Takes messages one at a time, in arrival order, which keeps each resort's
      swipes in order.
    - Parses and validates each message. Malformed or misrouted messages go
      straight to the dead-letter queue.
    - Applies the swipe through the aggregator, then acks it manually.
    - If processing throws, it retries in place with exponential backoff, then
      dead-letters the message after the maximum attempts.
    - When the standings change, it publishes a snapshot to the fanout exchange
      (best-effort).
    - stop() finishes the current message, then closes the channel so the broker
      requeues anything not yet acked.

  Aggregation

  - LeaderboardAggregator: the shared state you specified.
    - skierVertical (key resort:day:skier) holds each skier's accumulated
      vertical.
    - resortLeaderboards (key resort:day) holds a TopN per resort and day.
    - swipesProcessed counts applied swipes, not duplicates.
    - It also keeps a bounded set of recent eventIds per resort for dedup. An ID
      is recorded only after its swipe is applied.
    - apply() returns CHANGED, UNCHANGED or DUPLICATE. snapshot() builds the
      update to broadcast.
  - TopN: the thread-safe top-N ranking for one resort and day.
    - It's updated incrementally instead of re-sorted, which works because
      totals only grow.
    - Ties go to the lower skierID.
    - It reports whether the standings changed and keeps a version number that

❯ what does ResortWorker class do?                                              

⏺ ResortWorker (consumer/src/main/java/consumer/ResortWorker.java) is one
  consumer thread. It reads swipe events from the resort queues it's assigned,
  updates the leaderboard state, and acks each message. ConsumerPool creates N
  of them and splits the resorts among them round-robin.

  What each worker has

  - Its own RabbitMQ channel (line 52), with basicQos(prefetch), so each resort
    queue can have at most 100 unacked messages by default. Only the worker's
    own thread acks, rejects or publishes on that channel.
  - One processing thread named resort-worker-{i} (line 54).
  - A local queue of received messages (deliveries, line 41).

  How a message flows

  1. subscribe(resortID) (line 58) starts consuming one resort queue with manual
     ack. The RabbitMQ client's own thread doesn't process anything. It only
     drops each received message into deliveries (line 63).
  2. run() (line 94) is the worker's loop. It takes one message at a time, in
     arrival order. Because each resort queue belongs to exactly one worker, a
     resort's swipes are always handled one after another, in order.
  3. handle() (line 107) processes each message:
     - Parse and validate with parse(). A message that can never succeed is
       rejected straight to the dead-letter queue (skitrak.dlq) without
       retrying. That covers malformed JSON, a missing eventId, a resortID that
       doesn't match the queue, or a zero or negative field.
     - Apply with aggregator.apply(event):
       - DUPLICATE: the eventId was already seen, so it's counted and acked
         without changing anything.
       - CHANGED: the top-N changed, so it calls broadcast().
       - UNCHANGED: the skier's total went up but the top-N didn't change, so
         it's just acked.
     - Ack with basicAck, which happens only after the update is applied.
     - On an exception, it retries in place with exponential backoff (100 ms,
       then 200 ms, …). After maxAttempts (3 by default) it rejects the message
       to the dead-letter queue. While it's retrying, later messages from that
       resort wait, which keeps their order.

  Broadcasting

  broadcast() (line 145) publishes a full snapshot of that resort and day's
  top-N as JSON to the skitrak.leaderboard fanout exchange. Every WebSocket
  server's relay picks it up.

  It's best-effort. A failed publish is logged but doesn't block the ack,
  because the next change sends a complete snapshot again. Messages are
  transient (deliveryMode(1)) for the same reason: each update replaces the
  previous one.

  Stopping

  stop() (line 76) is used when the pool resizes or shuts down:
  1. It sets running = false, so the current message finishes and is acked.
  2. It waits up to 10 s for the thread. If the thread is stuck in a retry
     backoff, it interrupts it, and that message stays unacked.
  3. It closes the channel. The broker then puts every received-but-unacked
     message back on its queue in the original order. The next worker gets them,
     and if one had already been applied, dedup skips it.

  Failure handling

  - Ack fails because the connection dropped: it's counted in ackFailures. The
    broker redelivers the message after reconnect, and dedup stops it from being
    counted twice.
  - Counters: duplicates, retries, deadLettered, ackFailures and broadcasts all
    go up on the shared ConsumerPool counters. ConsumerApp logs them every 10 s.

❯ So we deal with the duplicated messages in LeaderboardAggregator class,       
  right?                                                                        

  Searched for 2 patterns, read 1 file (ctrl+o to expand)

⏺ Yes. Duplicates are detected in LeaderboardAggregator.apply()
  (consumer/src/main/java/consumer/LeaderboardAggregator.java:49-64).
  ResortWorker only reacts to the result: when apply() returns DUPLICATE, it
  increments the duplicates counter and acks the message so it leaves the queue.

  How it works

  Map<String, Boolean> seen = recentEventIds.computeIfAbsent(e.getResortID(), r
  -> boundedSet(dedupWindow));
  if (seen.containsKey(e.getEventId())) {
      return Outcome.DUPLICATE;                 // nothing is changed
  }
  // ... add vertical to skierVertical, update TopN ...
  seen.put(e.getEventId(), Boolean.TRUE);       // recorded only after the swipe
  was applied
  swipesProcessed.incrementAndGet();

  - What counts as a duplicate: a message whose eventId has already been
    applied. The server assigns that ID with UUID.randomUUID()
    (server/src/main/java/server/SkierServlet.java:110) before publishing.
  - Remembered IDs: each resort keeps its own LinkedHashMap of recent IDs. Once
    it holds CONSUMER_DEDUP_WINDOW entries (200,000 by default), the oldest are
    dropped.
  - Why the ID is recorded last: it goes into the set only after the vertical
    and the top-N are updated. If apply() throws partway through and the message
    is retried, the retry isn't mistaken for a duplicate.
  - Why no lock is needed: checking the set and then applying the swipe are two
    separate steps. That's safe only because each resort queue is handled by one
    worker at a time: single-active-consumer on the queue, plus the pool
    stopping old workers before starting new ones during a resize.

  Which duplicates it catches

  1. Broker redelivery: a message was applied but its ack never reached the
     broker, for example because the connection dropped or a worker stopped
     during a resize. The broker sends it again with the same eventId.
  2. Server publish retry: the publisher resent after a lost publisher confirm
     (server/src/main/java/server/messaging/SwipeEventPublisher.java:55). The
     same JSON, with the same eventId, is sent twice.

  What it doesn't catch

  - A client resending its HTTP POST. Suppose the server published the swipe but
    the client timed out and sent the request again. The server generates a new
    UUID for the second request, so the consumer sees two different events and
    counts the vertical twice. Catching this would require the client to send
    its own request ID and the server to use it as the eventId, which isn't
    implemented.
  - A consumer restart. The seen-ID set lives only in memory. After a restart it
    starts empty, and so do all the totals, so the old state is gone anyway.
  - A duplicate arriving after 200,000 newer events for that resort, by which
    point the original ID has been dropped. Redeliveries and publish retries
    arrive within seconds, so in practice this doesn't happen.

  ConsumerIntegrationTest checks this end to end: it publishes 12 duplicate
  messages and asserts that exactly 12 are counted as duplicates while each
  skier's totals stay correct.

  1. The client closes the channel or connection. This happens in
     ResortWorker.stop() and on shutdown.
  2. The TCP connection drops. The broker sees the socket close.
  3. The client stops responding. ConsumerConfig.connectionFactory() sets a 30 s

  4. Safety net: RabbitMQ's consumer_timeout, 30 min by default, closes any
     channel that holds a delivery unacked for that long.

  and requeues the message.

  The code doesn't check this itself. It relies on the client library and the

  consumer ResortWorker --publish--> skitrak.leaderboard (fanout)
                                       ├──> queue of server A --> relay A -->

  - Stop: the listener closes it on undeploy (line 58).

  start() (line 59) runs the first connection attempt on a background daemon
  thread, retrying every retryMs until RabbitMQ is reachable. So the web app
  still starts if the broker is down; it just has no live leaderboard until the
  relay connects. The warning is logged once rather than on every retry.

  connect() (line 110) sets up this server's subscription:
  1. Opens its own connection, named skitrak-leaderboard-relay-{serverId}. It's
     separate from the ChannelPool the server uses to publish swipes.
  2. Declares the skitrak.leaderboard fanout exchange. That's safe to repeat
     with matching settings, so it doesn't matter whether the server or the
     consumer starts first.
  3. Declares a queue just for this server:
     - Server-named (""): RabbitMQ picks a unique name, so each server gets its
       own queue.
     - Exclusive and auto-delete: the queue belongs to this connection and
       disappears when the server stops, so dead servers don't leave queues
       behind.
     - x-max-length=1000, x-overflow=drop-head: if the server falls behind, the
       oldest updates are dropped. Each message is a full snapshot, so losing
       older ones is harmless.
  4. Binds the queue to the fanout exchange and consumes it with auto-ack. No
     manual ack is needed, because a lost update is replaced by the next full
     snapshot.
  5. If anything fails, it aborts the connection and the retry loop tries again.
     If close() was called meanwhile, it discards the new connection.

  Automatic recovery (constructor, lines 50–52): after the connection drops, the
  client reconnects, recreates the queue (with a new name), rebinds it, and
  resubscribes.

  forward() (line 161) runs on RabbitMQ's delivery thread. It parses the JSON
  into Update, whose fields resortID, dayID, version, generatedAt and top match
  the consumer's LeaderboardUpdate. It then calls
  LeaderboardEndpoint.broadcast(...). That method stores the snapshot as the
  latest board for the resort and sends it to that resort's subscribers in
  resortSubscribers. Malformed messages are logged and skipped.

  close() (line 93) sets closed and closes the connection, which also deletes
  the server's queue.

  Why a fanout with one queue per server

  A WebSocket client is connected to only one server, while the consumer that
  computes the leaderboard is a separate process. The fanout delivers every
  update to every server, so each server can serve its own clients without
  knowing about the others. With a single shared queue, each update would reach
  only one server, and clients on the other servers would miss it.

  Limitations

  - Updates are lost while disconnected. The exclusive queue is deleted with the
    connection, so updates sent during an outage are lost. Clients catch up at
    the next standings change for their resort, which sends a full snapshot. A
    resort whose standings don't change keeps showing its old board.
  - A slow client delays everything. forward() runs on the delivery thread, and

    limit stops the queue from growing without limit, but the delay remains.
  - No tests. As noted in the known gaps, there are no unit tests for the relay

⏺ For one resort and day, yes: in normal operation the server receives the
  snapshots in the order they were produced, so the later board always arrives
  after the earlier one. That order comes from how messages are produced and
  delivered, not from timestamps. Nothing sorts by time, and the server doesn't
  check the order.

  Why the order holds for one resort and day

  1. One producer per resort. Only one ResortWorker thread handles a resort's
     queue at a time, because of single-active-consumer plus one worker per
     queue. It applies swipes one by one and publishes each snapshot right after
     the swipe that changed it, so the snapshots leave in order. TopN.version
     goes up by 1 on each change (TopN.java:52).
  2. RabbitMQ keeps order on a channel. Messages published on one channel and
     routed to the same queue are enqueued in publish order. Fanout doesn't
     change that: each server's queue receives them in the same order.
  3. The relay consumes them in order. Each server's queue has a single consumer
     on a single channel. The Java client delivers to it one message at a time,
     so forward() → LeaderboardEndpoint.broadcast() runs in queue order.
  4. Resizing keeps the order too. When a resort moves to another worker, the
     old worker finishes its current message and closes its channel before the
     new worker is created. Closing waits for the broker to confirm, and by then
     the old worker's published snapshots are already in the queues. So the new
     worker's first snapshot still lands after the old worker's last one.

  Across different resorts there's no ordering. Snapshots for resorts 1 and 5
  come from different threads and interleave arbitrarily. That's harmless,
  because each resort and day has its own board.

  Where it can still go wrong

  ┌──────────────────────┬──────────────────────────────────────────────────┐
  │         Case         │                      Effect                      │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │ Queue overflow       │ The oldest snapshots are dropped. Some are       │
  │ (x-max-length 1000,  │ skipped, but none arrive out of order.           │
  │ drop-head)           │                                                  │
  ├──────────────────────┼──────────────────────────────────────────────────┤

  │                      │ rest still arrive in order.                      │
  ├──────────────────────┼──────────────────────────────────────────────────┤
  │                      │ The standby starts with empty state. Its first   │
  │ Failover to a second │ snapshot has version 1 and lower totals, yet it  │
  │  consumer process    │ arrives after the first process's newer one. The │
  │                      │  board goes backwards.                           │
  └──────────────────────┴──────────────────────────────────────────────────┘

  The server doesn't check the version

❯ Do you think it will be  better to check the version and we throw the old

⏺ Yes, but only if the check also identifies which consumer run produced the
  update. A plain version comparison would make things worse than having no
  check at all.

  Why a plain version check is risky

  TopN.version lives in memory and starts again at 1 every time the consumer
  restarts. Suppose the server has cached version 5,000 for resort 3, day 1, and
  then the consumer restarts on EC2 after a crash, a redeploy or an
  auto-restart:

  - The new consumer sends versions 1, 2, 3, …
  - The server discards all of them as older than 5,000.
  - That leaderboard stays frozen until the new consumer has made 5,000 more
    changes for it.

  So on its own, the check turns a rare problem (the board briefly going
  backwards after a failover) into a common one (boards frozen after every
  consumer restart).

  What works: add an epoch to the update

  Give each consumer run an epoch: the time the process started, fixed for the
  whole run. Compare updates by (epoch, version):

  // LeaderboardEndpoint.broadcast(), per resortID:dayID
  boolean newer = cached == null
          || u.epoch > cached.epoch                                // a newer 
  consumer run wins
          || (u.epoch == cached.epoch && u.version > cached.version); // same 
  run: higher version wins
  if (!newer) return;   // stale: drop it, do not send

  - Same consumer run: higher versions win, so a stale or out-of-order snapshot
    is dropped.
  - Restart or failover: the new run has a larger epoch, so its first update is
    accepted right away and nothing freezes.
  - Old run sends late: if the old process's messages arrive after the new run
    has started, they have the smaller epoch and are dropped.

  The comparison only looks at epochs and versions from the same consumer run,
  or from runs started at clearly different times, so small clock differences
  between EC2 instances don't matter. That's why I wouldn't compare generatedAt
  timestamps directly.

  The change is small:
  - ConsumerApp sets a start time.
  - LeaderboardUpdate gains an epoch field.
  - On the server, LeaderboardRelay.Update and Leaderboard gain the same field.
  - LeaderboardEndpoint.broadcast() does the comparison inside
    latest.compute(...).
  - A couple of unit tests on the server side cover it.

  My take

  - Right now it guards against almost nothing. With one consumer process,
    snapshots already arrive in order, as covered above.
  - It's cheap and makes the system more robust. With EC2 restarts, and if you
    later add a standby consumer, it guarantees that clients never see a board
    go backwards because of a late message.

  I'd add it, with the epoch. It's about 20 lines plus tests. One thing it can't

  Auto-restart: recover without a human

  There are two levels:

  1. Process level: the JVM exits or crashes. Run the consumer as a systemd 
     service on the EC2 instance with Restart=always. systemd restarts it within
     seconds, and also starts it when the instance reboots. This is the same
     unit file mentioned earlier for loading credentials from
     /etc/skitrak/consumer.env.

       restarting the whole process.
     - From outside: a cron job or systemd timer that calls /health and runs
       systemctl restart skitrak-consumer after several failures in a row.
     - AWS level: an Auto Scaling group with health checks that replaces the
       instance. That's heavier than this assignment needs.

❯ explain what the systemd unit file does                                       

  Read 1 file (ctrl+o to expand)

⏺ consumer/deploy/skitrak-consumer.service tells systemd, Linux's service
  manager, how to run the consumer as a background service on EC2. It starts the
  consumer at boot, restarts it whenever it exits, and keeps its logs. Section
  by section:

  Header comments (lines 1–10)

  These are notes only; systemd ignores them. They list the install commands and
  how to check the service:
  - cp ... /etc/systemd/system/: systemd looks for unit files there.
  - daemon-reload: makes systemd reread its unit files after you add or change
    one.
  - enable --now: enable starts it at every boot; --now also starts it
    immediately.
  - systemctl status: shows whether it's running, its PID, the time it last
    started, and its latest log lines.
  - journalctl -u ... -f: follows the consumer's logs live. Anything the JVM
    writes to stdout or stderr goes to the system journal, including the
    health-check warnings and the shutdown messages.

  [Unit]: what the service is and when it starts

  Line: Description=SkiTrak consumer
  Meaning: The name shown in systemctl status and in logs
  ────────────────────────────────────────
  Line: Wants=network-online.target
  Meaning: Asks systemd to bring the network fully up during boot
  ────────────────────────────────────────
  Line: After=network-online.target
  Meaning: Starts the consumer only after the network is up, so its first
  connection attempt to RabbitMQ doesn't fail at boot. If the broker still
  isn't reachable, ConsumerApp.connect() keeps retrying anyway.

  [Service]: how to run it

  Line: User=ec2-user
  Meaning: Runs the JVM as a normal user, not root. Change it if your instance's

  user differs, e.g. ubuntu on Ubuntu AMIs.
  ────────────────────────────────────────
  Line: EnvironmentFile=/etc/skitrak/consumer.env
  Meaning: Loads KEY=value lines as environment variables before starting:
  RABBITMQ_HOST, RABBITMQ_USERNAME, RABBITMQ_PASSWORD, and any CONSUMER_*
  setting. ConsumerConfig reads them. systemd reads the file as root, so it can
   stay root-only (chmod 600) while the JVM runs as ec2-user.
  ────────────────────────────────────────
  Line: ExecStart=/usr/bin/java -XX:+ExitOnOutOfMemoryError -jar 
  /opt/skitrak/ski-consumer-1.0-SNAPSHOT.jar
  Meaning: The command that starts the consumer. The flag makes the JVM exit as
  soon as it runs out of memory. Without it, an out-of-memory error could kill
  worker threads and leave a broken process running. With it, the process exits
   and gets restarted. The JAR path must match where you copy it.
  ────────────────────────────────────────
  Line: Restart=always
  Meaning: Restarts the consumer every time it exits: a crash, kill -9, an
  out-of-memory exit, or the health check's exit(1). The only exception is when
   you stop it yourself with systemctl stop.
  ────────────────────────────────────────
  Line: RestartSec=5
  Meaning: Waits 5 s before each restart, so a consumer that keeps failing
  doesn't restart in a tight loop.
  ────────────────────────────────────────
  Line: SuccessExitStatus=143
  Meaning: On systemctl stop, systemd sends SIGTERM. The JVM runs the shutdown
  hook (stops workers, closes channels so unacked messages are requeued) and
  exits with code 143. This line tells systemd that 143 is a normal stop, not a
   failure.

  [Install]: what enable hooks it into

  WantedBy=multi-user.target is the normal boot state of a server. With it,
  systemctl enable makes the consumer start automatically on every boot,
  including after an EC2 stop and start.

  What happens in each case

  │           Event            │                   Result                   │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ The instance boots         │ systemd waits for the network, loads the   │
  │                            │ environment file, and starts the JVM       │
  ├────────────────────────────┼────────────────────────────────────────────┤
  │ The JVM crashes or is      │ After 5 s, systemd starts it again         │

    (x-single-active-consumer as a Boolean, and x-dead-letter-exchange).
    Otherwise delete them and let the consumer create them.

  1. Launch the consumer instance (AWS console)

  - AMI: Amazon Linux 2023.
  - Type: t3.small (2 GB) is comfortable. On a t2.micro (1 GB), add -Xmx700m to
    ExecStart later.
  - Network: same VPC as the RabbitMQ instance.
  - Security group consumer-sg, inbound:
    - SSH 22 from My IP
    - TCP 8081 from My IP, for /health
  - RabbitMQ's security group: add inbound TCP 5672 from consumer-sg. This lets
    the consumer reach the broker.

  2. Build and copy the files (on your Mac)

  cd ~/IdeaProjects/SkiTrak-Server-and-Client
  mvn -pl consumer clean package
  scp -i ~/path/to/key.pem \

      consumer/deploy/skitrak-consumer.service \

  sudo mkdir -p /opt/skitrak
  sudo mv ~/ski-consumer-1.0-SNAPSHOT.jar /opt/skitrak/

  RABBITMQ_HOST=172.31.x.x
  RABBITMQ_USERNAME=skitrak
  RABBITMQ_PASSWORD='your-password'
  CONSUMER_RESORT_IDS=1-10
  EOF

  nc -zv 172.31.x.x 5672          # must say "Connected"; if not, fix the

  sudo mv ~/skitrak-consumer.service /etc/systemd/system/
